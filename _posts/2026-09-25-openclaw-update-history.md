오픈클로(OpenClaw)를 블로그 글 작성이나 알림 자동화에 쓰다 보니, 이제는 오픈클로 자체를 관리하는 일도 생긴다. 업데이트를 확인하고, 설치하고, 기존 자동화가 잘 돌아가는지 살펴보는 일이다.

그런데 업데이트를 마쳤다고 생각했는데도 경고가 계속 보였다. 다시 확인해도 비슷한 메시지가 나오니, 설치가 실패한 것인지 다른 문제가 남은 것인지 구분하기가 어려웠다. 최근 대화에서 이 문제를 하나씩 확인하면서 알게 된 내용을 정리해본다.

이 글은 내 환경에서 겪은 일을 정리한 기록이다. 특정 버전의 전체 변경 사항을 소개하는 릴리스 노트나, 모든 환경에 적용할 수 있는 업데이트 매뉴얼은 아니다.

## 설치와 재시작 검증은 다른 일이었다

처음에는 업데이트 오류라고 하면 새 버전이 제대로 설치되지 않은 상황부터 떠올렸다. 하지만 당시 점검에서는 설치된 버전과 업데이트 대상 버전이 이미 같았고, 설치 자체보다 이후 상태 확인에서 문제가 드러났다.

Gateway를 재시작한 직후, 프로세스는 실행 중인데 WebSocket 연결은 아직 받을 준비가 되지 않아 `503`이 보인 경우가 있었다. 프로그램이 켜졌다는 것과 실제 요청을 처리할 준비가 끝났다는 것은 다른 상태였던 셈이다.

대화에서 확인한 진단은 재시작 검증 타이밍과 남아 있는 업데이트 상태 기록에 관한 것이었다. 이전 요청이 미완료 상태로 남아 있거나, 검증 실패 기록이 다시 보이면서 업데이트가 계속 실패하는 것처럼 보일 수 있었다.

그렇다고 업데이트 오류를 모두 기다리면 해결되는 문제로 볼 수는 없다. 이번 경험에서 얻은 기준은, 같은 업데이트를 반복하기 전에 무엇이 실패했는지 나눠서 확인하자는 것이다.

| 확인할 것 | 알고 싶은 것 |
| --- | --- |
| 설치된 CLI 버전 | 목표 버전의 설치가 반영됐는가 |
| 실행 중인 Gateway 버전 | 실제 서비스도 해당 버전으로 실행 중인가 |
| Gateway 연결 상태 | 프로세스 실행을 넘어 요청을 받을 수 있는가 |
| 플러그인 로드 상태 | 필요한 기능이 현재 런타임에서 정상적으로 올라오는가 |

## `Update history`는 현재 오류 목록이 아니었다

더 헷갈렸던 것은 CLI 명령을 실행할 때마다 나타나는 `Update history`였다. 경고가 눈앞에 계속 나오니, 방금 수행한 명령에서도 같은 문제가 발생했다고 읽기 쉬웠다.

하지만 최근 점검에서 확인한 이 영역은 **이전 업데이트 때 저장된 경고 이력**이었다. 메시지에도 다음과 같은 안내가 있었다.

> a later repair may have resolved them

이후 복구 작업으로 이미 해결됐을 수도 있다는 뜻이다. 과거에 문제가 있었다는 기록과 지금도 문제가 있다는 진단은 같지 않았다.

실제로 대화 중에는 설정 관련 경고를 수정한 뒤 현재 검사에서는 해당 경고가 사라졌지만, 업데이트 이력에는 예전 내용이 남아 있는 경우가 있었다. 이때 필요한 것은 경고 문구를 없애려고 같은 수정을 반복하는 일이 아니라, 현재 검사 결과와 과거 기록을 구분하는 일이었다.

현재 설정 경고를 확인할 때 사용한 명령은 다음과 같다.

```sh
openclaw doctor --lint
```

다만 이 검사에서 특정 경고가 사라졌다고 해서 모든 점검이 끝난 것은 아니다. Gateway 연결, 플러그인 동작, 별도의 보안 감사는 각각 확인할 범위가 있다. “이 경고가 해결됐다”와 “전체가 정상이다”를 섞지 않는 것이 중요했다.

## CLI가 정상이어도 대화창에는 바로 반영되지 않을 수 있다

9월 25일 업데이트 관련 점검에서는 CLI와 Gateway 버전이 `2026.9.6`으로 일치했고, Gateway 연결과 설정 유효성도 정상으로 확인됐다. Signal과 Telegram 역시 정상이라는 결과를 받았다. 이는 그때의 점검 결과이지, 이 버전이 언제나 최신이라는 의미는 아니다.

한편 Workboard는 CLI가 정상인데도 이미 실행 중인 대화 세션에는 전용 도구가 보이지 않았다. 당시에는 새 실행부터 반영될 가능성이 있다는 설명까지 확인했고, 그 대화에서 새 세션의 반영 결과까지 확인한 것은 아니었다.

이 사례도 비슷한 구분을 요구했다. 설치된 기능, 실행 중인 서비스, 현재 대화가 사용할 수 있는 도구가 반드시 동시에 바뀌는 것은 아니었다. 대화창에서 기능이 보이지 않는다는 이유만으로 설치부터 다시 할 필요는 없겠다는 생각이 들었다.

## 업데이트 관리도 대화의 주제로 분리하기

이런 일을 몇 차례 겪고 나니 업데이트는 한 번 명령을 실행하고 끝내는 작업보다는, 점검 결과를 이어서 남겨두는 작업에 가까웠다. 그래서 최근에는 오픈클로 업데이트를 다루는 대화도 따로 두기로 했다.

앞으로는 업데이트할 때 다음 정도를 함께 남겨두려고 한다.

- 어떤 버전에서 어떤 버전으로 바꾸었는지
- 재시작 후 실제 연결과 필요한 기능을 확인했는지
- 남은 메시지가 현재 경고인지 과거 이력인지
- 아직 확인하지 못한 부분은 무엇인지

오픈클로의 편한 점은 이런 확인도 대화로 이어갈 수 있다는 것이다. 오류 메시지를 가져와 원인을 살펴보고, 수정한 뒤 다시 점검하는 흐름을 한곳에 남길 수 있다. 다만 설명을 받았다는 사실과 실제 확인이 끝났다는 사실은 구분해야 한다.

이번에 배운 것은 단순하다. **업데이트 후 경고가 보이면, 먼저 그 경고가 언제의 어떤 상태를 가리키는지 확인하자.** 설치 결과와 현재 실행 상태, 과거 기록을 나눠 보기만 해도 다음에 무엇을 해야 할지가 훨씬 명확해진다.
