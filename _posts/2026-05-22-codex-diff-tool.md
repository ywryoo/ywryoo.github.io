업무를 하다 보면 두 문서를 나란히 놓고 어디가 바뀌었는지 확인해야 할 때가 자주 있다. 메일로 받은 문장, 계약서 일부, 보고서 문단, 안내문 초안처럼 길지는 않지만 한 글자 차이가 중요한 텍스트가 특히 그렇다.

처음에는 눈으로 대충 훑어보면 될 것 같지만, 실제로는 날짜 하나, 조사 하나, 숫자 하나가 바뀌어도 놓치기 쉽다. 그렇다고 매번 외부 diff 서비스를 쓰기에는 민감한 업무 문장을 넣어도 되는지 애매하다. 그래서 블로그 안에 바로 열어 쓸 수 있는 작은 문서 비교 도구를 만들기로 했다.

이번 작업은 Codex를 사용해서 진행했다. 목표는 단순했다. GitHub Pages로 운영 중인 Jekyll 블로그에 `_tools/diff.md` 페이지를 만들고, 업무 중 바로 사용할 수 있을 정도로 기능을 조금씩 업그레이드하는 것이었다.

![문서 비교 도구 화면](/assets/img/posts/diff-tool-codex-screenshot.png)

## 만들고 싶었던 것

처음에 필요했던 기능은 두 텍스트를 입력하고 차이를 보여 주는 것이었다. 하지만 실제 업무에서 쓰려면 단순히 "다르다"를 알려 주는 것만으로는 부족했다.

- 원본 문서와 비교 문서를 나란히 입력할 수 있어야 한다.
- 행 단위, 단어 단위, 글자 단위 비교를 선택할 수 있어야 한다.
- 공백 차이나 대소문자 차이를 무시할 수 있어야 한다.
- 전체 문맥을 볼지, 변경된 부분만 볼지 선택할 수 있어야 한다.
- 결과를 복사해서 메일이나 메신저에 붙여 넣을 수 있어야 한다.

특히 한국어 문장을 비교할 때는 글자 단위 비교가 중요했다. "7일"이 "5영업일"로 바뀌거나, 날짜의 월과 일이 바뀌는 정도는 행 단위 비교만으로는 눈에 잘 들어오지 않는다. 그래서 기본 비교 단위는 글자로 두고, 필요할 때 행이나 단어 단위로 바꿀 수 있게 했다.

## Codex로 페이지 만들기

Codex에게 먼저 저장소 구조를 확인하게 했다. 이 블로그는 Chirpy 테마 기반의 Jekyll 사이트이고, 별도 도구 페이지는 `_tools` 컬렉션에 넣으면 `/tools/.../` 형태로 접근할 수 있다. 그래서 새 도구는 `_tools/diff.md`에 만들었다.

페이지는 Markdown front matter 아래에 HTML, CSS, JavaScript를 함께 넣는 방식으로 구성했다. 별도 빌드 도구를 추가하지 않고 Jekyll만으로 배포할 수 있게 하려는 선택이었다. 작은 도구 하나를 위해 npm 패키지나 번들러를 늘리는 것보다, 정적 페이지 안에서 끝나는 편이 이 저장소에는 더 잘 맞았다.

처음 만들어진 화면은 두 개의 textarea와 비교 버튼 정도였다. 이후 실제로 사용할 상황을 생각하면서 기능을 계속 추가했다. 입력한 글자 수와 행 수를 보여 주고, 원본과 비교 문서를 바꾸는 버튼을 넣고, 결과 복사 버튼도 추가했다. 비교 옵션은 툴바로 묶어서 한눈에 보이게 정리했다.

## 비교 로직 업그레이드

핵심 로직은 두 텍스트를 토큰으로 나눈 뒤, 가장 긴 공통 부분을 찾아 차이를 계산하는 방식이다. 행 단위일 때는 줄을 토큰으로 보고, 단어 단위일 때는 공백을 기준으로 나누고, 글자 단위일 때는 문자 단위로 나눈다.

글자 단위 비교에서는 한국어 조합 문자가 어색하게 쪼개지지 않도록 `Intl.Segmenter`를 사용할 수 있으면 사용하게 했다. 브라우저가 지원하지 않는 경우에는 일반 배열 변환으로 처리한다. 완벽한 전문 diff 엔진은 아니지만, 블로그 안에서 바로 쓰는 업무용 도구로는 충분한 균형이라고 봤다.

또 하나 신경 쓴 부분은 비교 옵션이다. 공백을 무시하면 줄바꿈이나 띄어쓰기 차이 때문에 결과가 과하게 표시되는 일을 줄일 수 있다. 대소문자 무시는 영문 약어나 코드 조각을 비교할 때 유용하다. "변경만 보기"는 문서가 길 때 실제로 달라진 부분만 빠르게 확인하기 위한 기능이다.

## 화면 다듬기

업무용 도구는 예쁘기보다 덜 피곤해야 한다. 그래서 화면은 블로그 테마의 기본 색상과 카드 스타일을 따라가게 했다. 원본과 비교 문서는 좌우로 배치하고, 좁은 화면에서는 위아래로 쌓이도록 반응형 스타일을 넣었다.

결과 영역은 삽입된 부분을 초록색, 삭제된 부분을 붉은색으로 표시한다. 글자 단위 결과에서는 삭제된 글자는 취소선으로, 추가된 글자는 배경색으로 보여 주도록 했다. 덕분에 날짜, 숫자, 조사처럼 작은 변경도 눈에 빨리 들어온다.

복사 기능도 넣었다. 업무 흐름에서는 결과를 확인하는 것만큼 공유하는 일도 중요하다. 비교 결과를 그대로 복사해서 메일이나 메신저에 붙여 넣을 수 있으면, "어디가 바뀌었는지"를 설명하는 시간이 줄어든다.

## Codex를 쓰면서 좋았던 점

이번 작업에서 Codex는 단순히 코드를 대신 써 주는 도구라기보다, 작은 웹 도구를 빠르게 구체화해 주는 짝 프로그래머에 가까웠다. "두 문장을 비교하고 싶다"는 요구를 말하면, 저장소 구조를 확인하고, Jekyll 페이지 형식에 맞춰 파일을 만들고, 필요한 HTML/CSS/JavaScript를 한 번에 이어서 작업할 수 있었다.

물론 방향은 사람이 잡아야 한다. 어떤 기능이 실제 업무에 필요한지, 외부 라이브러리를 추가할지 말지, 결과를 어느 정도까지 자세히 보여 줄지는 직접 판단해야 했다. Codex는 그 판단을 코드로 옮기는 속도를 크게 줄여 주었다.

이런 작은 도구는 미뤄 두면 계속 미뤄진다. 하지만 한번 만들어 두면 매번 같은 문제를 만날 때 시간이 줄어든다. 이번 `_tools/diff.md`도 그런 종류의 작업이다. 거창한 서비스는 아니지만, 업무 중 자주 생기는 작은 불편을 블로그 안의 도구 하나로 덜어낸 셈이다.

## 다음에 해볼 것

지금도 바로 쓰기에는 충분하지만, 더 다듬을 부분은 남아 있다. 자주 비교하는 문장을 임시로 브라우저에 저장하거나, 붙여 넣은 문서의 앞뒤 공백을 정리하는 옵션을 넣을 수 있다. 비교 결과를 더 보기 좋은 HTML 형태로 내보내는 기능도 생각해 볼 만하다.

중요한 것은 이런 개선을 어렵게 생각하지 않아도 된다는 점이다. 필요한 순간에 요구사항을 짧게 적고, Codex와 함께 페이지를 조금씩 고치면 된다. 그렇게 블로그는 글을 올리는 공간이면서, 내가 자주 쓰는 작은 업무 도구를 쌓아 두는 공간이 될 수 있다.
